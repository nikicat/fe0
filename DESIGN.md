# Fe0 compiler design

How the compiler is built. [SPEC.md](SPEC.md) defines what Fe0 means, and [PLAN.md](PLAN.md)
covers scope and schedule. This document fixes the decisions that would otherwise cost the first
days of the build window.

Guiding rules:
- Prefer the simplest thing that is correct.
- The input programs are small (a few KB), so linear scans and fixed-size encodings are fine.
- Every shortcut is marked with a `ponytail:` comment in the code, naming its limit.

## 1. Repository layout (in the window)

```
fe0/            ingot: the compiler as a library; no I/O, target-agnostic
  src/lexer.fe  tokens
  src/ast.fe    arena AST
  src/parser.fe recursive descent
  src/check.fe  names, types, constants, effects
  src/codegen.fe AST → EVM ops with labels
  src/asm.fe    label resolution, initcode/runtime layout
  src/diag.fe   error codes and positions
  src/io.fe     the `Source` effect and its adapter, BytesReader (`text` and `bytes`)
fe0-cli/        ingot: native `main`, stdin → hex on stdout
fe0-chain/      ingot: Front / Back / Compiler contracts (on-chain split, §8)
corpus/         Fe0 programs (*.fe) + call scripts (*.calls); generated ones under corpus/gen/
tests/          ingot: differential tests generated by tools/embed.py
tools/          embed.py, gen.py (random programs), corpus_scan.py
```

The `fe0` library is shared by every target. Only the edge ingots know where bytes come from.

## 2. Lexer

- **Input:** the lexer pulls bytes one at a time through `uses (input: mut Source)` and keeps one
  byte of lookahead. It appends each byte to the source buffer, a `Text`, as it reads it.
  `Source` is fe0's own effect, and WORKAROUNDS.md says why it is not std I/O.
- **Tokens** are spans of the source buffer, so the lexer never copies the text. `Token` is
  declared in `fe0/src/lexer.fe`.
- **Keywords:** compared against `String<N>` constants (`s.as_bytes()[i]`, see TODO §1).
- **Newline tokens** are kept. Inside parentheses the lexer drops them, since it already tracks
  paren depth; anywhere else the parser decides whether a newline ends a statement (SPEC §3.4).
- **Positions:** line and column are computed only when an error is reported, by scanning the
  source buffer up to the error offset.

## 3. AST: an index-based arena

Fe has no recursive types without `unsafe`, so the AST lives in flat arrays and refers to nodes
by index. Index 0 means "none". A child list is a length-prefixed run in one array. `op` and `ty`
are typed fields, so operators and written types never travel as bare integers.
`fe0/src/ast.fe` declares `Ast`, `Node` and the fields of each node kind.

- **Building lists:** one stack, `Parser.pending` in `fe0/src/parser.fe`, serves all lists, since
  inner lists close before outer ones.
- **Interning:** a linear scan over `syms`, in `Ast.intern`.
- **Check results go in side tables indexed by node** (`types: MemVec<Ty>`,
  `res: MemVec<usize>`). The AST itself is never mutated after parsing.

## 4. Parser

- Recursive descent, one function per grammar rule in SPEC §3.1.
- Binary expressions use precedence climbing with the SPEC §3.2 table.
- **No error recovery:** the first error ends the parse. `parse()` reports it in `Ast.err`
  instead of returning a `Result`, for the reason in WORKAROUNDS.md (IR0600).
- **Recursion is bounded:** nesting depth is capped at `MAX_DEPTH` in `fe0/src/parser.fe` (§8a).
- **Statement terminators** follow SPEC §3.4. Any other token after a statement is
  `P_EXPECTED_END`.

## 5. Checker

The checker makes one pass over items to collect names, then one pass over bodies.

- **Types:** the checker reuses `Ty` from `fe0/src/ast.fe` and adds a unit type, for blocks and
  calls that have no value. Every expression node gets one.
- **Scopes:** a stack of `Local { sym, ty, mutable, frame_slot }` plus a stack of scope marks.
  Lookup scans from the top. A local named like a storage field is an error (SPEC §5.2).
- **Constants:** evaluated during checking with the same checked arithmetic as runtime. Overflow
  gives `C034` and division by zero `C025`, mirroring Fe's `3-0034`/`3-0025`. Only earlier
  constants may be referenced.
- **Effects:** each `init`/arm gets two `u256` bitmasks over the contract's fields, `may_read`
  and `may_write`, built from its `uses` (one bit per field, at most 256 fields).
  - A field read checks `may_read`, an assignment checks `may_write`.
  - Free functions have both masks zero, so any field access in them is an error.
  - Entries that are never used produce a warning. Duplicates are an error.
- **Return paths:** a function body must end in a value of the return type, or every path must
  end in `return`. This is checked on the AST, with "always returns" computed bottom-up.

## 6. Code generation

### 6.1 Memory layout

| Range | Use |
|---|---|
| `0x00–0x3f` | Scratch: return value, panic payload head |
| `0x40` | **FP**, the current frame pointer |
| `0x60–0x7f` | Reserved (EVM convention, unused) |
| `0x80…` | Frames, growing upward |

**Frames.** Each function has a frame of `2 + params + locals` words at FP:
- `[FP+0]` saved FP of the caller;
- `[FP+32]` return address;
- `[FP+64…]` parameters, then locals.

Every local has a fixed slot assigned by the checker, with no slot reuse
(`ponytail: frame size = all locals; reuse slots if gas matters`).

### 6.2 Calling convention

**Caller:**
1. Evaluate the arguments left to right onto the stack.
2. `newFP = FP + caller_frame_size`.
3. Store the arguments into `[newFP+64+32i]`, the return label into `[newFP+32]`, and FP into
   `[newFP+0]`.
4. Set `FP = newFP` and `JUMP` to the callee.

**Callee on return:** the result is on the stack. It restores `FP = [FP+0]` and jumps to the
saved return address.

This supports recursion, and memory grows with call depth. Gas bounds both recursion depth and
memory cost.

### 6.3 Expressions

Each expression leaves exactly one word on the stack (unit-typed ones leave nothing).

| Construct | Emitted |
|---|---|
| Literal | `PUSHn` (the minimal n) |
| Local | `MLOAD(FP + off)`: `PUSH1 0x40 MLOAD PUSHn off ADD MLOAD` |
| Field *i* | `PUSHn i SLOAD` |
| `a + b` | eval a, eval b, `DUP2 ADD`, `DUP1 SWAP2 GT` → `JUMPI panic_11` |
| `a - b` | eval a, eval b, `DUP1 DUP3 LT` → `JUMPI panic_11`, `SWAP1 SUB` |
| `a * b` | `MUL`, then if `a != 0 && r / a != b` → `panic_11` |
| `a / b`, `a % b` | `b == 0` → `panic_12`, then `DIV`/`MOD` |
| `<< >>` | `SHL`/`SHR` with operands swapped. They never fail (SPEC §4) |
| `&& \|\|` | Short-circuit with `JUMPI` |
| Comparisons | `LT GT EQ`, plus `ISZERO` for `<= >= !=` |
| `!b` | `ISZERO`. `~a` is `NOT` |
| `assert!(c)` | `c ISZERO JUMPI panic_01` |
| `assert!(c, "m")` | `JUMPI` to an inline block that `MSTORE`s `Error(string)` and `REVERT`s |

The stack sequences in this table are sketches. The exact sequences get pinned down by unit
tests that run the emitted code.

- **Panic stubs:** one shared block per code (`0x01`, `0x11`, `0x12`), emitted once per contract
  and only if used. Each stores `0x4e487b71 << 224` at 0 and the code at 4, then
  `REVERT(0, 0x24)`.
- **Control flow:** `if`, `while`, `break` and `continue` lower to labels and `JUMPI`. The
  codegen keeps a loop-label stack for `break` and `continue`.

### 6.4 Dispatcher (runtime entry)

Mirrors the official compiler (SPEC §6):

```
CALLVALUE → JUMPI revert_empty         ; all arms are non-payable
CALLDATASIZE 4 LT → JUMPI revert_empty
0 CALLDATALOAD 224 SHR                  ; selector
for each arm: DUP1 PUSH4 sel EQ → JUMPI arm_k
revert_empty: 0 0 REVERT
```

Each arm then:
1. Checks `CALLDATASIZE >= 4 + 32n`.
2. Loads each argument word, checks `bool ≤ 1` and `Address >> 160 == 0`, and stores it into
   the arm's frame.
3. Runs the body.
4. `MSTORE(0, result)` then `RETURN(0, 32)`, or `STOP` for unit.

- A single up-front `CALLVALUE` check is safe because every failing path reverts with empty
  data, so the order of checks is unobservable.
- `ponytail:` the arms are a linear chain of `EQ`s. Use a binary search over sorted selectors,
  like the official compiler, only if gas matters.

### 6.5 Deployment layout

```
[ initcode ][ runtime ][ constructor args, appended by the deployer ]
```

The initcode:
1. Checks `CALLVALUE == 0`. The official initcode also rejects value, so the CREATE fails
   (`init_with_value` in `spike-conform/src/init_args.fe`).
2. Checks `CODESIZE >= init_len + rt_len + 32n`.
3. `CODECOPY`s the arguments into the `init` frame and validates them as in the dispatcher.
4. Runs the `init` body.
5. `CODECOPY`s the runtime to memory 0 and `RETURN`s it.

`init_len` and `rt_len` are constants filled in by the assembler.

## 7. Assembler

- Code is emitted into a `MemVec<u8>`.
- **Jumps** always use `PUSH2 <label>` (`ponytail: fixed 2-byte targets, so code must stay under
  64 KB`). Each use is recorded as `(byte_offset, label)` in a fixup list.
- **Labels** emit `JUMPDEST` and record their offset.
- **Finish:** patch every fixup, then lay out the initcode and runtime as in §6.5.

There is a single pass with no relaxation, because the 2-byte targets keep offsets stable.

## 8. On-chain split (24 KB limit)

The lexer alone is 3.1 KB of runtime code, so the whole compiler won't fit in one contract.

| Contract | Message | Does |
|---|---|---|
| `Front` | `parse(bytes src) -> bytes` | lex, parse, check, then serialize nodes, lists, syms, types and frame sizes |
| `Back` | `emit(bytes ir) -> bytes` | deserialize, codegen, assemble, return deploy code |
| `Compiler` | `deploy(bytes src) -> address` | `STATICCALL` Front then Back, then `create_raw` |

- **Serialization format:** the arrays are dumped as 32-byte words with length prefixes. No
  schema; both sides are compiled from the same `fe0` ingot.
- **Day 1–3 measurement decides the cut:** if `Front` alone exceeds 24 KB, split the checker
  into its own contract.
- Errors cross the boundary as `Error(string)`-style revert data that carries the `Diag`.

## 8a. Measured limits of the host (official Fe on the EVM)

Measured Oct 28 on master `d217a51bf` (`spike-limits/`, 30M gas per call):

- **`MemVec` growth is linear:**
  - 237 gas per pushed byte at 1k, 4k and 16k items;
  - three interleaved vectors (bytes, 5-field nodes, `u32` lists) cost 851–902 gas per item.

  So the arena design is affordable: about 1M gas for the AST of a 2 KB program.
- **Recursion depth is bounded by the EVM stack, not by gas:** at most **1,019** nested calls
  for a one-argument function. Fe keeps return addresses on the 1,024-slot EVM stack, and
  functions with more live values get less depth.
  - **Consequence:** the parser caps nesting depth and reports `P008` "nesting too deep"
    instead of crashing with a stack overflow.
  - **Measured with the real parser** (Nov 4, Fe 26.5.1). At `-O 0`, 20 nested parentheses
    parse and 22 overflow the EVM stack. That is about 45 stack slots per parenthesis. Nested
    blocks cost less, and 12 of them parse. At `-O 2`, every probe up to 28 parentheses parsed,
    and 28 was the largest one tried.
  - **The cap:** `MAX_DEPTH` is 20 depth steps. A function body and its outer expression take
    2 steps, each parenthesis takes 1, and each block inside a block takes 2. So the cap allows
    18 nested parentheses or 9 nested blocks, which keeps a margin at `-O 0`. Only optimized
    builds could take a higher cap.
  - This limits only the compiler running on chain. Code *generated by* Fe0 keeps its frames
    in memory (§6.1), so it has no such limit.
- **`fe test` does not enforce EIP-170:** 24,577 and 49,152-byte runtimes deploy fine.
  - The harness therefore asserts sizes itself: Fe0's own contracts (Front, Back, Compiler) at
    most 24,576 bytes of runtime code, and Fe0's output for every corpus program likewise.
  - The initcode limit (EIP-3860, 49,152 bytes) is presumably not enforced either; check it
    the same way.
  - **A real node does enforce it.** Local `anvil` (Foundry 1.8.4, hardfork BPO1) deploys a
    24,576-byte runtime and rejects 24,577 bytes (status 0).
  - So the final gate is a deploy script: `anvil` plus `cast send --create`, run in CI and before
    any Sepolia deploy. A Fe-built `.bin` deploys and works there: the spec Counter returns
    `get() = 2` after two increments, and its on-chain runtime size equals `fe build`'s
    `.runtime.bin` (99 bytes).

## 9. Diagnostics

Every phase reports an error as a `Diag`. `fe0/src/diag.fe` declares it and defines how codes
are numbered and printed. The message comes from a table indexed by code.

| Phase | Examples |
|---|---|
| Lexer | bad character, unterminated string, literal over 256 bits |
| Parser | expected token, end of statement, chained comparison |
| Names | unknown name, duplicate item, local shadows a field |
| Types | mismatch, missing return path |
| Effects | field not in `uses`, write without `mut`, unknown field, duplicate entry |
| Constants | overflow (`C034`), division by zero (`C025`) |

The CLI prints `file:line:col: CODE message`. On chain, the message is the code, the line and
the column.

## 10. Differential test harness

`tools/embed.py` turns each `corpus/X.fe` (plus `X.calls`) into `tests/src/x.fe`:

1. A copy of the program as a module, compiled by the official compiler.
2. `const SRC: [u8; N] = [...]`, the same source as bytes.
3. One `#[test]` that:
   1. deploys the official build with `evm.create2<C>(args)`;
   2. compiles `SRC` with the `fe0` library *inside the test*, so on the EVM;
   3. deploys Fe0's output with `create_raw`;
   4. replays every call in `X.calls` against both contracts with `try_call_raw`;
   5. asserts that the success flag and the returndata bytes are equal, including revert
      payloads;
   6. asserts that Fe0's runtime code is at most 24,576 bytes and its initcode at most
      49,152 bytes, because the test EVM enforces neither (§8a).

**Contract names must be unique across the whole test ingot.** Two modules that each define
`contract C` crash the official compiler (WORKAROUNDS.md). `embed.py` therefore renames each
program's contract to `C_<file>`, and the generator emits unique names. Path dependencies
between ingots work (`spike-deps/user`). Embedding sources as large `const [u8; N]` arrays is
fine too: 32 KB compiles and runs, with about 3 s to build three such files (`spike-harness/`).

**Call scripts** list one call per line: selector, argument words, and optionally a value. They
are hand-written for the hand corpus and emitted by the generator for generated programs.

**Negative tests:** `corpus/reject/*.fe` carry a header such as `// expect: E116 12:9`. The test
runs Fe0 and checks the diagnostic. Separately, `fe check` must also reject the file (any error
counts), which keeps the subset rule honest.

## 11. Random program generator (`tools/gen.py`)

- **Deterministic per seed.** Each run emits `corpus/gen/s<seed>.fe` and its `.calls` file.
- **Shape:**
  - 1–4 `mut` fields;
  - 1–6 arms with random `uses` (always sufficient: unused entries allowed, no violations);
  - 0–3 pure helper functions, called from arms.
- **Expressions:** random trees over `u256`/`bool` with depth up to 5, using every operator,
  `if`-expressions and helper calls. Literals are biased toward edge values (0, 1, 2²⁵⁵,
  2²⁵⁶−1) so checked arithmetic actually panics sometimes.
- **Loops:** only `var i = 0; while i < K { …; i += 1 }`, where `K` is at most 8 and the body
  never assigns `i`, so every loop terminates.
- **Calls:** 5–20 random calls per program, mixing valid arguments with malformed calldata cases
  (short data, `bool = 2`, dirty `Address`).
- **Oracle:** the official compiler, through the harness in §10. A mismatch prints the seed.
  Shrinking is a stretch goal (delete statements and re-test).
- **Batching** (measured Oct 28, 8 cores, 200 small 3-arm contracts):

  | Layout | Time for 200 |
  |---|---|
  | One ingot | 35.4 s (~175 ms each) |
  | 200 standalone files, `--jobs 0` | 39.7 s |
  | Same, `--jobs 1` | 96 s |
  | **8 ingots × 25, `--jobs 0`** | **18.4 s** |

  - Standalone files can't depend on the `fe0` ingot, so the harness uses **batch ingots of
    about 25 programs**, each depending on `fe0` by path, all run in one
    `fe test --jobs 0 batch*` invocation.
  - **A program that fails to compile fails only its batch** (`batchN::compile`, while the other
    batches still run). The runner then re-runs that batch split in halves to find the
    culprit.
  - Expected throughput is about 10 programs per second before Fe0's own in-EVM compile is
    added, so a 1,000-program round takes a few minutes.
  - Note: master still accepts out-of-range literals (`let x: u8 = 300` silently gives 44);
    open PR #1883 makes that an error. This doesn't affect Fe0, which only has `u256`.

## 12. Hashing (`sol("…")` selectors, a stretch goal)

- Hashing is an effect, `uses (h: mut Hasher)`:
  - the EVM provider calls the `KECCAK256` opcode;
  - the native provider is a software keccak-f[1600] in Fe, because 26.5.1 cannot lower
    `EvmKeccak256` natively (WORKAROUNDS.md).
- **Feasibility checked Oct 28** (`spike-keccak/`): one full round (theta, rho, pi, chi, iota)
  over `[u64; 25]` gives the same digest on EVM, native and a Python reference
  (`01ac8e14a6e6ea79`).
  - `u64` shifts discard overflowing bits, like `u256`, so `rotl` is `(x << n) | (x >> (64 - n))`.
- **Cost:** about 28k gas per round on the EVM (-O1 and -O2), so about 680k per permutation.
  That's why the EVM provider must use the opcode, while the software version runs natively
  only.
- Remaining work for the window: padding (`0x01 … 0x80`, rate 136 bytes), absorbing input,
  and testing against known vectors (`keccak("answer()") = 0x85bb7d69…`).

## 13. Testing per phase

| Phase | Unit tests (`fe test`) |
|---|---|
| Lexer | Token streams for each token class; error positions |
| Parser | Node-shape assertions for each grammar rule; a reject test for each `P` error |
| Checker | One accept and one reject per rule in SPEC §5–6, with error code and position |
| Codegen | Assemble small snippets, `create_raw` them, and check results (the `create_raw` probe pattern) |
| Assembler | Fixups, and layout lengths against the bytes produced |
| End-to-end | The §10 harness over `corpus/`, `corpus/reject/` and `corpus/gen/` |
